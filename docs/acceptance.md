# 実機受入れ

サービス登録と電源設定を扱う項目は実機を変更する手動検証です。通常の `make test` とは分離します。物理的な閉蓋を含む項目は自動テストの成功だけで検証済みにしません。メニューバーUIの確認には、下記の模擬電源を使う検証用アプリを利用します。

## 準備・導入

1. `make check` を実行し、全テストと両方の release build が成功することを確認します。
2. 旧版の `sudo dopa`、他の抑制ツールを終了します。`pmset -g` で SleepDisabled が 0 であることを確認します。
3. 一般ユーザーから `sudo .build/release/dopa-daemon install` を実行します。実行元が分からない場合は `--user USER` を指定します。
4. `launchctl print system/dev.dopa.daemon` でサービスの登録を確認します。`dopa-daemon status` と `status --json` は sudo なしで成功し、セッションなし・idle・確認値 false であることを確認します。
5. 配置した実行ファイル・plist は root 所有で一般ユーザーが変更できず、`/var/db/dopa` は 0700 であることを確認します。別ユーザーからはソケット API を操作できないことを確認します。

## セッション

1. sudo なしで `.build/release/dopa` を起動し、status と `pmset -g` の SleepDisabled 1 を照合します。
2. 別端末でも dopa を起動し、2 セッションを確認します。一方を Ctrl+C、もう一方を SIGTERM で終了し、最後の終了後だけ SleepDisabled 0 と復元記録の削除を確認します。
3. `dopa -d` と通常の dopa を併用します。`pmset -g assertions` で表示 assertion を確認し、`-d` 側の終了で表示 assertion だけが解除されることを確認します。
4. dopa の PID に SIGKILL を送り、接続断による解除を確認します。
5. 外部ディスプレイを外し、dopa と秒ごとの時刻を記録する別プロセスを動かして蓋を約 1 分閉じます。開いた後に記録の連続性と `pmset -g log` を照合します。通信の継続だけで判断しません。
6. `dopa -l` と通常の dopa を併用し、閉蓋で `-l` 側だけが終了することを確認します。`dopa -dl` でも表示 assertion の解除を確認します。

## 障害・管理

1. dopa 稼働中にデーモンへ SIGKILL を送ります。launchd が再起動し、記録を復旧することを確認します。旧 CLI は異常終了し、自動再取得しないため、復旧後はセッションなしとなります。
2. 再起動後に status と新しい dopa が利用できることを確認します。
3. セッション稼働中に `sudo dopa-daemon install` を再実行し、既存セッションの終了・復元・更新後の稼働を確認します。
4. `sudo dopa-daemon uninstall` を実行し、復元後にサービスと管理ファイルが削除され、CLI 自体は残ることを確認します。status は接続不能で非ゼロ終了します。
5. 復元失敗・配置失敗は模擬テストで確認します。実機で復元に失敗した場合は管理ファイルや復旧記録を手動削除せず、エラーを保存して復旧します。

手動の `sudo pmset disablesleep 0` は、dopa と他ツールが動いていないことを確認できた場合の最終的な復旧手段です。

## メニューバーUIの検証範囲と環境制約

2026-09-13時点で、ネイティブ入力・状態遷移・パネル配置と実際のNSPopoverの位置安定は自動テストで確認しています。一方、この環境ではCUAによるアプリ取得が繰り返しタイムアウトし、デスクトップ上の実パネルを通した操作確認は完了できませんでした。以下はその制約による未検証範囲です。

手動確認または操作可能な環境で再検証する場合は、`mise exec -- scripts/run-ui-fixture.sh` で模擬電源の検証用アプリを起動できます。専用バンドル・一時ソケット・ダミー認可を使い、実際の電源設定を変更しません。終了時はスクリプトが自身のテストプロセスと一時ファイルを片付けます。

- 実パネルのLiquid Glass・アクセント色・ダーク表示と、透明度・動き・コントラストのアクセシビリティ設定への追従。オフスクリーン画像だけでは素材や色の合成を判定できません。
- 両タブ、無制限、開始・停止、編集・適用・キャンセル、入力・エラーpopover・一覧スクロールを、デスクトップ上の操作として通した確認。
- 実際のキャンセルボタンによるdraft破棄とフォーカス解除。対応するオフスクリーンAXテストもボタンを取得できずスキップしており、モデル操作の成功では実ボタンの確認を代替していません。
- 停止確認のキャンセル、停止後のフォーカス移動、右クリックメニューからの終了を、デスクトップ上の操作として通した確認。

検証用アプリは実際の管理者認証画面を使いません。実OSの管理停止の認証・キャンセルは、実サービスを操作する別の受入れ項目です。

実ビルドのdaemon導入UIは、次の順で確認します。

1. サービスをuninstallしてDopa.appを起動し、未導入ダイアログが表示されることを確認します。「キャンセル」では管理者認証が表示されず、管理ファイルも作成されないことを確認します。
2. Dopa.appを再起動して「続ける」を選び、その後にだけmacOSの管理者認証が表示されることを確認します。認証後、同梱daemonが現在のUIDを許可ユーザーとして導入され、UIが再接続することを確認します。
3. Dopa.appの起動中に `sudo dopa-daemon stop` を実行し、接続断で注意アイコンへ変わることを確認します。注意アイコンの左右クリックでは通常のpopoverやメニューではなく起動確認が表示され、「続ける」の後だけ管理者認証とdaemon起動が行われることを確認します。
4. Dopa.appの起動中にdaemonをuninstallし、アウトライン月へ変わることを確認します。アウトライン月の左右クリックでは通常UIではなく未導入ダイアログが表示されることを確認します。再導入・再接続後のアイドル表示が塗りつぶし月になることも確認します。
