# 実機受入れ

サービス登録と電源設定を扱う項目は、実機の状態を変更する手動検証です。通常の `make test` とは分けて実施します。物理的なふたの開閉を含む項目は、自動テストの成功だけでは検証済みにできません。メニューバーUIの確認には、次の模擬電源を使う検証用アプリを利用します。

## 準備・導入

1. `make check` を実行し、全テストと両方の release build が成功することを確認します。
2. 旧版の `sudo dopa` と、他のスリープ防止ツールを終了します。`pmset -g` で SleepDisabled が 0 であることを確認します。
3. 一般ユーザーから `sudo .build/release/dopa-daemon install` を実行します。実行元が分からない場合は `--user USER` を指定します。
4. `launchctl print system/dev.amas.dopa.daemon` でサービスの登録を確認します。`dopa-daemon status` と `status --json` は sudo なしで成功し、セッションなし・idle・確認値 false であることを確認します。
5. 配置した実行ファイル・plist は root 所有で一般ユーザーが変更できず、`/var/db/dopa` は 0700 であることを確認します。別ユーザーからはソケット API を操作できないことを確認します。
6. 旧版の `dev.dopa.daemon` を導入した状態から新版のinstallを実行し、旧サービスと旧管理ファイルが削除され、許可ユーザーを維持した `dev.amas.dopa.daemon` だけが稼働することを確認します。

## セッション

1. sudo なしで `.build/release/dopa` を起動し、status と `pmset -g` の SleepDisabled 1 を照合します。
2. 別のターミナルでも dopa を起動し、2 セッションを確認します。一方を Ctrl+C、もう一方を SIGTERM で終了し、最後の終了後だけ SleepDisabled 0 と復元記録の削除を確認します。
3. `dopa -d` と通常の dopa を併用します。`pmset -g assertions` で表示 assertion を確認し、`-d` 側の終了で表示 assertion だけが解除されることを確認します。
4. dopa の PID に SIGKILL を送り、接続断による解除を確認します。
5. 外部ディスプレイを取り外し、dopa と毎秒時刻を記録する別プロセスを動かしたまま、ふたを約 1 分閉じます。開いた後に記録の連続性と `pmset -g log` を照合します。通信が続いているだけで判断しません。
6. `dopa -l` と通常の dopa を併用し、ふたを閉じると `-l` 側だけが終了することを確認します。`dopa -dl` でも表示 assertion の解除を確認します。

## 障害・管理

1. dopa 稼働中にデーモンへ SIGKILL を送ります。launchd が再起動し、記録が復旧することを確認します。旧 CLI は異常終了し、セッションを自動的に再取得しないため、復旧後はセッションなしとなります。
2. 再起動後に status と新しい dopa が利用できることを確認します。
3. セッション稼働中に `sudo dopa-daemon install` を再実行し、既存セッションの終了・復元・更新後の稼働を確認します。
4. `sudo dopa-daemon uninstall` を実行し、復元後にサービスと管理ファイルが削除され、CLI 自体は残ることを確認します。status は接続不能で非ゼロ終了します。
5. 復元失敗・配置失敗は模擬テストで確認します。実機で復元に失敗した場合は、管理ファイルや復旧記録を手動で削除せず、エラーを保存したうえで復旧します。

手動の `sudo pmset disablesleep 0` は、dopa と他のツールが動いていないことを確認できた場合の最終的な復旧手段です。

## メニューバーUIの検証範囲と環境制約

2026-09-13時点で、ネイティブ入力・状態遷移・パネル配置と実際のNSPopoverの位置の安定性は自動テストで確認しています。一方、この環境ではCUAによるアプリの操作が繰り返しタイムアウトし、デスクトップ上の実パネルを通した操作確認は完了できませんでした。以下はその制約による未検証範囲です。

手動確認または操作可能な環境で再検証する場合は、`mise exec -- scripts/run-ui-fixture.sh` で模擬電源の検証用アプリを起動できます。専用バンドル・一時ソケット・ダミー認可を使い、実際の電源設定を変更しません。終了時はスクリプトが自身のテストプロセスと一時ファイルを片付けます。

- 実パネルのLiquid Glass・アクセント色・ダーク表示と、透明度・動き・コントラストのアクセシビリティ設定への追従。オフスクリーン画像だけでは素材や色の合成を判定できません。
- 両タブ、無制限、開始・停止、編集・適用・キャンセル、入力・エラーpopover・一覧スクロールを、デスクトップ上で実際に操作して通す確認。
- 実際のキャンセルボタンによるdraft破棄とフォーカス解除。対応するオフスクリーンAXテストもボタンを取得できずにスキップしており、モデル操作の成功では実ボタンの確認を代替していません。
- 停止確認のキャンセル、停止後のフォーカス移動、右クリックメニューからの終了を、デスクトップ上で実際に操作して通す確認。

検証用アプリは実際の管理者認証画面を使いません。実OSの管理停止の認証・キャンセルは、実サービスを操作する別の受入れ項目です。

実ビルドのdaemon導入UIは、次の順で確認します。

1. 別のAppを前面にした状態で、サービスをuninstallしたDopa.appを起動します。Dopaがアクティブになって未導入ダイアログがkey windowとして表示され、ReturnとEscapeがそれぞれ「続ける」と「キャンセル」に反応することを確認します。「キャンセル」では管理者認証が表示されず、管理ファイルも作成されないことを確認します。
2. Dopa.appを再起動して「続ける」を選び、その後でのみそのMacの `sudo` PAM認証が始まることを確認します。`sudo_local`に `pam_tid` やWatch認証を構成した端末ではパスワード入力なしで成功することを確認します。PAMがターミナルの文字入力を求める構成では、PTY上の認証と導入操作が中止され、ターミナルから `sudo` で実行するよう案内が表示されて管理ファイルが変更されないことを確認します。認証成功後は同梱daemonが現在のUIDを許可ユーザーとして導入され、管理ファイルの導入完了後からUIが再接続するまでは回転する進捗表示となり、一瞬も注意アイコンにならないことを確認します。daemonが応答しない場合は10秒で接続待ちを終了し、エラーダイアログと注意アイコンへ移ることも確認します。
3. Dopa.appの起動中に `sudo dopa-daemon stop` を実行し、接続断で注意アイコンへ変わることを確認します。注意アイコンの左クリックでは通常のpopoverではなく起動確認が表示され、「続ける」の後だけ管理者認証とdaemon起動が行われることを確認します。
4. Dopa.appの起動中にdaemonをuninstallし、管理ファイル削除後0.5秒程度でアウトライン月へ変わることを確認します。アウトライン月の左クリックでは通常UIではなく未導入ダイアログが表示されることを確認します。再導入・再接続後のアイドル表示が塗りつぶし月になることも確認します。
5. 未導入・停止中・認証待ちを含む各状態で右クリックメニューから終了できることを確認します。Dopaがactiveな状態ではCommand-Qでも終了でき、認証待ちなら認証子プロセスをキャンセル・回収してから終了することを確認します。
